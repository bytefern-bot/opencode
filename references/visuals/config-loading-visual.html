opencode 配置加载机制

不是单个配置文件读取，而是一条分层流水线：找到多个来源，统一解析校验，按优先级合并， 再加载目录扩展、企业覆盖和运行时兼容逻辑。

发现来源

global、project、.opencode、env、console、managed 都可能提供配置。

解析校验

先替换变量，再 JSONC 解析，最后用 Config.Info schema 验证。

3

深度合并

后加载覆盖前加载；对象深合并；instructions 追加去重。

4

目录扩展

从配置目录加载 command、agent、mode、plugin，并记录插件来源。

5

组织覆盖

console org config、managed config、macOS MDM 后置合并。

6

最终整理

mode 转 agent，tools 转 permission，应用 runtime flags。

7

缓存重载

InstanceState 缓存；invalidate 通过 dispose instance 触发重载。

为什么看起来复杂：它不只是在读 JSON

用户与项目叠加

个人默认值和仓库规则都要生效。项目配置不能抹掉用户所有偏好，只覆盖需要覆盖的部分。

monorepo 局部规则

根目录可以定义通用规则，子包可以覆盖模型、instructions、agent 或 MCP。

企业强制策略

provider、enterprise URL、权限策略需要能由组织或系统管理员最后覆盖。

扩展是文件系统资源

command、agent、plugin 更适合以目录文件维护，所以配置目录同时承担扩展发现。

合并规则：不是所有字段都一样

标量字段

后加载覆盖前加载。

{
  "model": "github-copilot/gpt-5"
}

对象字段

使用 deep merge。局部字段覆盖，同级未设置字段保留。

{
  "permission": {
    "bash": "ask",
    "edit": "allow"
  }
}

instructions

特殊处理：追加并去重，用来叠加个人、团队和目录规则。

[
  "global.md",
  "AGENTS.md",
  "team-rules.md"
]
普通字段靠加载顺序覆盖 对象字段深合并 instructions 追加去重 plugin 保留 source 和 scope

路径发现逻辑

ConfigPaths.files("opencode", cwd, worktree)

  • 向上查找 opencode.jsonc 和 opencode.json。
  • 停止在 worktree 边界。
  • 结果 toReversed()，所以父级先加载，子级后覆盖。

ConfigPaths.directories(cwd, worktree)

  • 包含全局配置目录。
  • 包含项目向上的 .opencode 目录。
  • 包含 home 下的 .opencode。
  • 包含 OPENCODE_CONFIG_DIR。

重载模型

缓存在哪里

  • global config 用无限 TTL 缓存。
  • instance config 由 InstanceState 缓存。
  • 消费者通常只调用 Config.Service.get()。

Config.invalidate()

  • 清掉 global cache。
  • Instance.disposeAll()。
  • 发布 disposed event。
  • 下一次访问重新跑整条加载流水线。

一句话总结

这套机制复杂，是因为 opencode 把“用户偏好、项目规则、目录扩展、SDK 注入、企业管控、兼容迁移、实例生命周期” 都统一到了同一个配置入口。好处是所有运行入口看到一致的最终配置；代价是加载函数承担的职责偏多。
查看结果：opencode debug config
主入口：Config.Service.get()
重载：Config.invalidate()
